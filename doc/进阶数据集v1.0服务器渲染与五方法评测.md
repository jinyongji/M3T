### 3.1 此前的可选受限方案（本次不启用）

本节保留此前配置供将来需要时参考；当前按第0节恢复原始资源调度。

2026-10-18用户提供的只读检查确认：

| 项目 | 实际状态 | 本次处理 |
|---|---|---|
| CPU | 两插槽、48物理核、96逻辑CPU；编号n与n+48为同核超线程 | 新渲染限制为24–31及72–79，共8物理核、16逻辑CPU，均在NUMA节点1 |
| CPU允许范围 | 0–95；内存节点0–1 | 不修改正在运行的旧评测的绑定或线程策略 |
| 当前数据盘 | `/home`→`/dev/sdb1`，29.1T，ROTA=1，ext4 | 旧评测继续读原目录；新渲染仍写原目录时存在共享I/O |

| I/O调度器 | sdb为mq-deadline；NVMe为none | I/O优先级仅作辅助，不承诺带宽或零干扰 |
| GPU拓扑 | `nvidia-smi topo -m` 返回失败 | 上述CPU选择只根据CPU拓扑，未证实与GPU7的NUMA距离最优 |

此前的受限入口执行 `taskset --cpu-list "$ADVANCED_RENDER_CPUS" nice -n 15 ionice -c 3 ...`，并限制OpenBLAS/MKL/NumExpr线程为1。CPU范围、nice与I/O类由后台控制器及其Blender/FFmpeg子进程继承。CPU绑定限制可运行的核心范围，并不声明Blender总共只创建16个线程。当前按用户要求恢复 `render.sh`，不再应用上述资源策略。

这属于**减轻争用**：旧评测仍允许系统在0–95上调度，其他用户也可能使用相同核心；此入口不会为我们预留CPU。共用物理盘、缓存、内存带宽和后台写回仍可能影响耗时。I/O空闲类可能使渲染明显变慢，实际效果取决于运行内核、调度器与I/O路径；不是固定MB/s限速。Linux官方说明：[CPU亲和性](https://man7.org/linux/man-pages/man1/taskset.1.html)、[I/O优先级](https://docs.kernel.org/block/ioprio.html)。

如需稳定速度对比，应由管理员/调度器预留CPU与GPU、控制共享I/O，并在相同条件下另开五方法速度运行。当前准确率评测可继续；现有速度保留为共享负载下实测值，不能事后准确消除未知排队时间。

如果新渲染已经在运行，上传新版小包不会改变现有进程的资源策略。先只停止新渲染，再改用受限入口续跑：
